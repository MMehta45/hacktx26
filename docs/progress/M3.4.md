# Milestone 3.4 — Gemini reliability and candidate preservation

## Root cause

The reported warning came only from the `json.JSONDecodeError` branch. The final Gemini
response was therefore syntactically invalid JSON before candidate-level Pydantic
validation ran. The previous implementation did not request a response schema and did
not retain Gemini's finish reason, finish message, output token count, or invalid-response
location. It is not possible to honestly distinguish historical token truncation from a
different syntax defect after the fact. The 4,000-token cap and large duplicated schema
made truncation a credible risk, but it is not claimed as a verified historical fact.

Only the deterministic remote-work candidate and mechanic shortlist existed before that
single extraction call. All transit, assistance, extension, and dynamic candidates were
created afterward from the parsed JSON, explaining why eight investigated hypotheses
could collapse to two visible cards and one seeded question.

## Implemented

- Gemini extraction now requests `application/json` with the Pydantic-generated
  `ResearchExtraction` JSON schema, uses deterministic temperature, and allows up to
  7,000 output tokens.
- `ResearchExtraction.model_validate_json` handles syntax, missing fields, unexpected
  types, and domain validators in one boundary.
- One bounded retry receives a sanitized validation error. Diagnostics distinguish
  malformed JSON, schema validation, truncation/continuation, and provider errors and
  retain finish reason/output-token metadata without raw output or credentials.
- Evidence-grounded fallback candidates are built before Gemini extraction. Repeated
  failure retains evidence, candidates, questions, events, warnings, and a completed
  research status when the provider research itself succeeded.
- Candidate IDs are deterministic; candidates carry `hypothesis_ids`; question references
  are validated; and exact semantic duplicates merge evidence/hypothesis links rather
  than silently replacing one another.
- Every hypothesis now has a typed `HypothesisOutcome` with candidate IDs, evidence IDs,
  status, and a reason suitable for Build 04 without prose re-parsing.

## Regression fixture

The repeatable eight-hypothesis/six-provider-call fixture forces both Gemini extraction
attempts to return truncated JSON after transit, web, Maps, and Maps Reviews evidence is
collected. The API preserves nine distinct candidates: remote work, three independently
confirmable dynamic options, transit, two mechanic estimate requests, baseline bill
assistance, and a separate dynamic local-aid option. All eight hypotheses receive a
traceable outcome and every question references an existing candidate.
