# Milestone 3.2 — Geographic grounding and multi-path research

Date: 2026-10-24

## Diagnosis

The prior one-search run was caused by the orchestration loop. It passed all graph targets
to Gemini in one broad request and immediately broke when Gemini returned no additional
tool calls. There was no pathway coverage state, no reserved per-path budget, and no
continuation for unvisited targets. The UI defaults also sent null route locations and
times, which made the transit guard reject any directions request. Candidate extraction
occurred after searching and did not cause the single provider call.

One additional live issue appeared during this correction: Google Maps search rejected
the adapter's `location` parameter without an `ll` zoom/map parameter. Places search now
adds the trusted city to the query instead of sending that invalid parameter.

## Implemented

- Locked editable Austin defaults for the geographic proxy home, fictional Whole Foods
  workplace, 08:00–16:00 weekday schedule, and personal-car context.
- Added diversity-aware pathway orchestration and pathway status contracts/events.
  Transportation, employer flexibility, mechanic alternatives, and bill assistance
  continue independently after empty or failed results.
- Restricted Gemini's exposed tools per active pathway. A model-selected transit intent
  expands to dated outbound/return requests for both affected shifts. Initial research
  reserves four calls for those legs plus one mechanic and one assistance call.
- Added normalized route numbers, stops, transfers, walking distance, observed fare,
  place address, rating, and available review snippets.
- Added deterministic enforcement that late/incomplete transit stays blocked or
  conditional, employer flexibility stays unconfirmed, and ratings alone cannot support
  an affordable-repair claim or invented price.
- Added pathway cards and richer provider evidence to the existing Explore layout.
  No optimizer, action application, or M2 financial changes were introduced.

## Live verification

A bounded pass used the existing live Nessie snapshot and all six initial SerpApi calls:

- Transportation: successful, four Google Maps Directions calls and four route evidence
  records covering outbound/return checks for two affected dates.
- Employer flexibility: explicitly conditional, zero public-provider calls.
- Repair alternatives: successful, one Google Maps places call and five listings.
- Bill assistance: attempted with one Google web call; that provider request failed in
  the final run and was reported without suppressing the other pathways.
- Result: 9 evidence records, three candidates across transportation, repair
  affordability, and income preservation; two priority-27 pending questions. The repair
  candidate remained conditional with unknown price. Overall status was `partial`
  because the assistance call failed.

An earlier post-fix live pass returned 14 evidence records across all three SerpApi
engines, with transportation, repair, and assistance pathways all successful. Candidate
extraction on that run lacked a sufficiently explicit compact output contract; M3.2 then
added the contract and separately verified Gemini returned valid JSON candidates and
questions.

## Remaining limits

- Live Gemini and SerpApi results vary and one pathway can still be inconclusive or fail;
  the response now exposes that per pathway.
- Directions evidence is limited to what Google Maps returns for future demo dates.
  Missing routes, times, fare, or return legs remain unknown.
- Maps review snippets are not comprehensive review analysis. Actual repair scope and
  written price remain required.
- Employer and landlord decisions, program eligibility, and provider timing cannot be
  verified by search. Build 04 will capture answers and test action combinations; it was
  not implemented here.
